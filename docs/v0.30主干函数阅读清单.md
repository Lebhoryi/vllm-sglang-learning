## 0. 阅读总原则

vLLM 是**配置驱动的框架**，不是算法。90% 代码在判断"用户配了啥 → 走哪条路"。
只跟**主干那条路**：单机、单卡、无 spec decode、无 KV connector、无 LoRA、无多模态。

**跳过信号**（看到就跳）：
- `if kv_transfer_config` / `if self.connector` → KV 传输分支
- `if spec_config` / `draft_token` → 投机解码分支
- `if lora_request` / `max_loras` → LoRA 分支
- `if mm_inputs` / `encoder_cache` → 多模态分支
- `_eep_` / `elastic` / `scale_up` → 弹性扩缩容
- `rocm` / `xpu` / `tpu` / `cpu` → 非 CUDA 后端

## 4. 调度层 · `vllm/v1/core/sched/scheduler.py`（3288 行）★ 重头戏

### 4.1 `schedule()` — L556–1518（963 行，实际精读约 400 行）

| 行号 | 段落 | 读什么 | 优先级 |
|---|---|---|---|
| L558–565 | **算法说明注释** | ★★★ **先读这段！** woosuk 写的：vLLM **没有 prefill/decode 阶段之分**，每个请求只有 `num_computed_tokens`，调度器每步给它分配 token | **★★★** |

| **L623–866** | **First, schedule the RUNNING requests** | ★★★ 已运行的请求优先：算能跑几个 token → 要新 KV block → 不够就**抢占最低优先级请求**（L1538 `_preempt_request`） | **★★★** |

| **L867–1515** | **Next, schedule the WAITING requests** | ★★★ 新请求：查前缀缓存命中（L523 `_get_local_prefix_cache_hit`）→ 决定这个 chunk 跑多少 → 分配 block | **★★★** |
| L1516–1517 | `_update_after_schedule` + return | 收尾统计 | ★ |

**读到什么**：
```
调度器每步的决策链：
    1. RUNNING 请求能跑吗？  → 能则跑，KV 不够则抢占别人
    2. WAITING 请求能进吗？  → 前缀缓存命中的部分直接跳过计算
    3. 输出 SchedulerOutput（哪些请求、各跑多少 token、用哪些 block id）
```

## 9. 一句话总结

```
LLM.generate()
  → InputProcessor.process_inputs()    文本 → token + 元数据
    → EngineCore.step()                ← 心跳
        → Scheduler.schedule()         谁跑、跑多少 token
            → KVCacheManager.allocate_slots()   给 block
        → GPUModelRunner.execute_model()        变 tensor、跑模型
        → Scheduler.update_from_output()        收 token、判停、释放 KV
  → RequestOutputCollector              结果回去
```

**这 9 个文件、约 2400 行，就是 vLLM 的全部主干。** 剩下 99 万行是配置分支、硬件后端、284 个模型实现、多模态、分布式——用哪个读哪个。
