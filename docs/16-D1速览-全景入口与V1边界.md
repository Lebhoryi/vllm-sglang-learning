## 一、全景与进程（`design/arch_overview.md` §V1 Process Architecture）

V1 是多进程架构，四个角色：

| 进程 | 干什么 | 数量 |
|---|---|---|
| **API Server** | 收 HTTP（OpenAI 类接口）、做输入处理（tokenization、多模态加载）、把结果流式吐回客户端 | 默认 1；开 DP 时自动 = DP 大小；可用 `--api-server-count` 覆盖 |
| **Engine Core** | **跑 scheduler、管 KV cache、协调模型执行**；一个 busy loop 不停地调度并把活派给 GPU worker | 每个 DP rank 一个（默认 1） |
| **GPU Worker** | 每个 GPU 一个进程：加载权重、跑 forward、管显存 | = TP × PP × DP（每卡一个） |
| **DP Coordinator** | 条件启动：DP > 1 时做负载均衡、给 MoE 协调同步 forward | DP > 1 时 1 个 |

- **IPC 是 ZMQ**：每个 API server 连**所有** engine core，多对多（任一 API server 可把请求路由到任一 engine core）。
- 进程数公式：`A + DP + N`（DP > 1 时再 +1）。官方例子：`-tp=4` → 1 + 1 + 4 = **6 个进程**；`-tp=2 -dp=4` → 4 + 4 + 8 + 1 = **17 个进程**。
- 一句话记住分工：**Engine core 是内循环（性能关键），API server 是外循环（可以承担开销）**——这句的完整版在 `design/metrics.md`（D2 读）。

⚠️ **同一页前半段是 V0 遗留**：`LLMEngine` / `AsyncLLMEngine` 那段指向 `vllm/engine/llm_engine.py`，那个路径在你源码里已经不存在了。只读 `V1 Process Architecture` 这一节。

## 二、请求的入口（`serving/online_serving/README.md`）

端点很多，但对内核学习者只需按"**进来之后走哪条路**"归成五类：

| 类别 | 代表端点 | 内核视角的意义 |
|---|---|---|
| OpenAI 兼容 | `/v1/chat/completions`、`/v1/completions`、`/v1/responses`、`/v1/embeddings`、`/v1/audio/*` | 你实际在用的那条路 |
| Anthropic 兼容 | `/v1/messages`、`/v1/messages/count_tokens` | 多一个前处理分支，后续同一条引擎路 |
| Pooling / 打分 | `/v1/embeddings`、`/pooling`、`/classify`、`/score`、`/rerank` | **不走生成**，直接取 hidden state —— 两条 runner 的分叉点 |
| 运维与观测 | `/health`、`/version`、`/v1/models`、`/load`、`/metrics`、`/start_profile`、`/stop_profile` | `/start_profile` 是 D4 profiling 的入口 |
| 调试 / 开发（`VLLM_SERVER_DEV_MODE=1`） | `/reset_prefix_cache`、`/reset_mm_cache`、`/sleep`、`/wake_up`、`/collective_rpc`、`/server_info` | `/reset_prefix_cache` 做 M7 前缀缓存实验时要用 |

两个值得单独记住的点：

1. **renderer / derenderer 是"前后处理被拆出去"的产物**：`/v1/chat/completions/render` 只做 tokenization + prompt 格式化 + 多模态预处理，返回 token id，不跑推理。反过来说明引擎主链路只吃 token。
2. **入口的差异只在前处理/后处理**，最终都汇到同一套 engine core + worker。所以 D1 不需要逐个端点看。

## 三、V1 的模块边界与 unified scheduler（`usage/v1_guide.md`）

**重写了哪些**：scheduler、KV cache manager、worker、sampler、API server。**沿用了哪些**：模型、GPU kernel、工具类。→ 你要精读的正是被重写的那五块。

**最核心的一段原文（含 note）**：

> V1 的 unified scheduler 把 prompt token 和 output token **同等对待**，用一个简单字典（如 `{request_id: num_tokens}`）给每个请求动态分配固定 token 预算 —— 于是 chunked prefill、prefix caching、speculative decoding 这些特性都**不需要在 prefill / decode 之间划出严格分相**。

调度策略：FCFS 与 priority（`--scheduling-policy`），**FCFS 作平局裁决**。

**V0 → V1 的行为变化（与你后续里程碑直接相关）**：

| 项 | V1 的行为 |
|---|---|
| Chunked prefill | **默认开**（V0 按模型特征条件开） |
| CUDA graph | 占用的显存比 V0 更多 |
| Logprobs | 默认返回 **raw**（未经 logits 后处理），可用 `--logprobs-mode` 改 |
| Prompt logprobs + 前缀缓存 | 不再缓存 logprobs；带 prompt logprobs 的请求**会忽略前缀缓存、整段重算 prefill** |

**V1 删掉了什么（这就是"没有 swap"的官方依据）**：

- 🔴 **GPU ↔ CPU KV Cache Swapping 已移除** —— 官方原话：新架构下处理抢占**不再需要 KV swap**。对应 D2 会读到的"V1 默认抢占 = RECOMPUTE"。
- 🔴 `best_of` 移除；🔴 per-request logits processors 移除（改成启动时设的**全局** logits processor）；🔴 request-level structured output backend 移除。
- 🟡 Concurrent partial prefills 仍在进行中。

**特性状态速查**：🟢 prefix caching / chunked prefill / LoRA / FP8 KV cache / spec decode / prompt logprobs + APC；🔴 best_of / per-request logits processors / GPU↔CPU KV swap。

> ⚠️ **一个要挂账的发现**：同一页说 Mamba 与 **hybrid 模型**（Mamba + 标准注意力）已被支持，但明确写着 *"prefix caching is not yet supported for any of the above models"*。你手上的 **Qwen3.5 是混合注意力**（GDN 线性注意力 + full attention）。如果这条在本版仍然成立，那 M7「prefix caching × chunked prefill × 混合注意力 三者怎么咬」的前提就要改。
> **不要现在就下结论** —— 文档可能滞后于代码。记一笔，到 M4/M7 用 `--enable-prefix-caching` + `/reset_prefix_cache` 在 0.8B 上实测确认。
