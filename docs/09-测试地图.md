## 2. 样例深读：test_mamba_align_chunk_split.py（388 行）

> 尝鲜样本（2026-09-11 精读）。它正是你 0.8B 日志金矿 `Setting attention block size to 784 tokens ... >= mamba page size` 的**官方回归测试**——把"现象 → 不变量 → 复现 → 修复断言"串成了完整故事。

### 2.1 背景（文件 docstring 即 bug 报告）

- **线上事故 #43559**：mamba "align" 缓存模式下，slot `p` 必须持有**恰好 `(p+1)×block_size` 个 token 之后**的 SSM 状态。
- 状态只在 chunk 结束点落盘；若 chunk 在 mamba 块中间结束，slot 里的"运行态"位置不对；后续跨越该边界的 chunk 会把 slot 当作完整快照发布（"publishes it anyway"）→ prefix cache 命中时恢复出**截断的状态**（poisoning）。
- 复现配置（注释明说 mirror 真实部署）：**Qwen3.6-27B**，mamba block 1600、MTP 3 个 draft token、prompt 短于 2 个 mamba 块。

### 2.2 不变量（全文件 12 个测试共同守护）

```
slot p 持有的 state == 恰好处理完 (p+1) × mamba_block_size 个 token 的状态
```

### 2.3 测试组织与手法

| 测试 | 手法 | 断言要点 |
|---|---|---|
| `test_mamba_prefill_checkpoint_valid` ×8 | 纯函数直测 `is_mamba_prefill_checkpoint_valid`（`kv_cache_interface.py:973`） | checkpoint 导出合法性：`query_start % hash_block_size == 0` + checkpoint 列在 初始列之后 + 对齐 16 |
| `test_internal_checkpoint_split` ×6 | `SimpleNamespace` stub 调真实 `Scheduler._mamba_block_aligned_split`（`scheduler.py:404`） | 有 checkpoint 列时非最终 chunk 截断到 1600 边界 |
| `test_partial_checkpoint_resume_stops_at_mamba_block_boundary` | stub + `partial_hit=True` | 哈希对齐续跑在物理块中间时**不能用**内部 checkpoint 列（会与初始态列混叠），保持对齐切分 |
| `test_disabling_eagle_block_drop_keeps_the_trailing_cache_boundary` | `use_eagle_block_drop` 开关 | drop=True → 尾部缓存到 1600；drop=False → 3200 |
| `test_fragmented_first_chunk...` / `test_fragmented_tail_chunk...` | **端到端仿真**：真实 `KVCacheManager` + `allocate_slots`，预算分片制造碎片，`_count_cached_boundary_states` 逐 slot 核对哈希 | 短首块（EAGLE 把 `last_cache_position` 置 0）不得把 slot0 从 state@364 发布成 state@1600 |
| `test_intermediate_chunk_ends_stay_block_aligned` ×5 | 参数化首块 800/900/1599/1601/2000 | 每个非最终 chunk 必须以 mamba 块边界结束 |
| `test_poisoning_is_block_size_independent` ×3 | `monkeypatch.setattr` 改模块级 `MAMBA_BLOCK_SIZE`（1536/12288） | 不变量按块成立——Kimi-K3 规模（TP8 ~1.5k、DEP16 ~12k）也不安全 |
| `test_unaligned_resume_never_runs_past_its_block` ×20 | 循环推进 + 逐段断言 | 块中间续跑必须先重对齐再跨边界（partial-hit 与 KV connector 外部 token 场景） |

### 2.4 与你的日志的因果链（闭合）

```
docs/02 附录 C：prefix caching 默认开 → mamba_cache_mode=align（models/qwen3_5.py:332 禁 all）
→ platform/interface.py:925-940：attn_block_size 提升直到 ≥ mamba page size，
   align 模式令 mamba_block_size = block_size
→ 你日志：Setting attention block size to 784 tokens ... >= mamba page size
→ scheduler 侧：need_mamba_block_aligned_split=True（scheduler.py:339/361）
   → 每次 prefill 切分走 _mamba_block_aligned_split（scheduler.py:404, 651-652）
→ 本测试文件守护的正是这段切分的正确性
```

### 2.5 五条"原来如此"（尝鲜结论）

1. **测试文件就是事故复盘报告**：docstring 第一段就是 bug 的完整因果，比 issue 还好读。
2. **不变量先行**：先写"slot p = (p+1)×block 的状态"，所有测试都是它的投影——读测试 = 拿到模块的**契约全集**。
3. **stub 手法**：`SimpleNamespace(block_size=..., cache_config=...)` 不实例化整个 Scheduler，直接把真实方法绑在假 self 上跑——"轻量替身测真实逻辑"是 vLLM 测试的主流套路。
4. **monkeypatch 全局**：改模块级常量即可测不同 block size（1536/12288），不用改被测代码。
5. **"发布时校验"**：`_count_cached_boundary_states` 逐块核对 `block_hash_num_tokens == state_at.get(block_id)`——哈希声称的状态必须等于实际持有的状态，这正是防污染的核心不变量。
6. **EAGLE block drop 是变量**：尾部缓存边界随 `use_eagle_block_drop` 变（1600 vs 3200），不是你日志里 784 的来源，但解释了"边界由谁定"。
