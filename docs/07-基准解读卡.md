## 二、指标含义与解读要点

| 指标 | 含义 | 解读注意 |
|---|---|---|
| Successful / Failed | 成功/失败请求数 | **先看这个**：有 failed 就找 `errors` 字段，别急着聊吞吐 |
| Request throughput (req/s) | 每秒完成请求数 | 受 `--request-rate inf`（打满）与 `--max-concurrency` 影响 |
| Output token throughput (tok/s) | 每秒输出 token 数（不含输入） | **服务商报价/自研栈对比最常用** |
| Total token throughput | 输入+输出总吞吐 | 负载长度不同不可直接比 |
| Peak concurrent requests | 观测到的最大并发 | ★ 会**大于** `--max-concurrency`（chunked prefill 让更多请求同时"在算"），实测 26 vs 16 |
| TTFT（均值/中位/P99） | 首 token 延迟 | ★ **不含客户端排队时间**！是纯服务端 prefill 表现 |
| TPOT（均值/中位/P99） | 每个输出 token 的间隔（不含首个） | 与"token/s 手感"互推（1/TPOT） |
| ITL | 相邻 token 间隔 | ★ **P99 常远大于均值**（实测 438ms vs 52ms）= 调度抖动信号 |
| E2EL / latency | 端到端延迟（服务端处理） | ★ 只在 json 的 `latencies` 里，终端不打印；公式见第三节 |
| `queue_times`（仅 json） | ★ 客户端排队时长 | 打满模式下 p50 可达数十秒，**与 TTFT 是两个维度，别混** |
| ~~RTFx~~ | ~~Inverse Real-Time Factor~~ | ⚠️ **文本 benchmark 恒为 0.0，无意义**。源码 `serve.py:779` = `input_audio_duration / dur_s`，**只对 ASR（音频）bench 有效**。旧版本卡说"v0.28 新指标，>1 表示比实时快"是错的 |

## 三、Sanity check（数对不对）清单

1. **failed == 0**（有错误先看 json 的 `errors`）
2. **输出长度达标**：`--random-output-len 128` → 平均实际输出长度应接近 128（过短 = 被 EOS/stop 截断，过长 = 忽略 EOS）
3. **吞吐量纲自洽**：request_throughput × (input+output)/req ≈ total_token_throughput
4. **TPOT 与吞吐互推**：单并发下 1/TPOT ≈ 每请求 token/s；多并发下吞吐 ≈ 并发数/（prefill+decode 混合成本）
5. **基线可比性**：对比时必须同 input-len/output-len/concurrency/request-rate——否则数字没有意义

```markdown
## 27B vLLM 基线（2026-09-29 01:28，正式版）
- 环境：49.147 node-worker-147，A100-80GB PCIe sm_80；vllm **0.30.0**（非 0.28）
- 起服务：`--max-model-len 16384 --max-num-seqs 16 --gpu-memory-utilization 0.9 --dtype bfloat16`
- 加载：权重 51.1 GiB；GPU 实占 71,531 MiB / 81,920 MiB (87%)
- 负载：random 512 in / 128 out，200 prompts，concurrency 16，request-rate=inf
- 结果：
    req/s              = 1.97
    output tok/s       = 251.53   (峰值 384.00)
    total tok/s        = 1257.63
    TTFT mean/median/P99 = 1324 / 1297 / 2289 ms
    TPOT mean/median/P99 = 51.88 / 51.94 / 62.19 ms
    ITL  mean/median/P99 = 51.88 / 42.00 / 438.37 ms
    latency mean/p50   = 7.913 / 7.892 s   (json latencies)
    queue  p50/max     = 45.05 / 95.41 s   (json queue_times)
- 失败：0 / 200
- json：logs/openai-infqps-concurrency16-Qwen3.8-27B-20260929-013006.json
- 终端 log：logs/bench-27b-vllm-0929-0128.log
- 备注：见下方"三个时间维度"与"两个异常"
```

### ★ 三个时间维度必须分开看（实测核心洞察）

| 维度 | 值 | 含义 | 数据来源 |
|---|---|---|---|
| **TTFT** | 1324 ms | 服务端**纯 prefill**，**不含排队** | 终端 + json |
| **E2EL / latency** | 7.91 s | 服务端**一次完整处理**（prefill+decode） | 仅 json |
| **queue_time** | p50 **45.1 s** | 客户端**排队等待**（打满模式，16 并发位抢 200 请求） | 仅 json |

**三者关系已验证**（公式精确成立，偏差 0.01%）：

```
E2EL = TTFT + (output_len - 1) × TPOT
     = 1324.2ms + (128-1) × 51.88ms
     = 7.913 s    ← 实测 latency 均值 7.913 s  ✓
```

**排队时间分桶**（200 请求）：
```
<10ms（立即调度）    16 个   ← 正好等于 --max-concurrency=16
10ms ~ 5s             0 个
>5s（严重排队）     184 个   ← 其余全在排队，最长 95.4s ≈ 整个 bench 时长
```

> ★ **解读要点**：`request-rate=inf` 是把 200 个请求**瞬间全部打进**，只有 16 个能立刻跑，其余排队。所以 **queue_time 反映的是压测方式，不是服务性能**；真正衡量服务端的是 TTFT / TPOT / throughput。

### 两个值得追的异常

**① ITL P99 = 438 ms，是中位数（42 ms）的 10.4 倍**

```
mean_itl = 51.88   median_itl = 42.00   p99_itl = 438.37   std = 63.83
```

中位数**低于**均值 + P99 极高 = **少数请求被严重打断**。根因是 chunked prefill：新请求的 prefill 分块插入，打断正在 decode 的请求。

**② 实测吞吐 251.5 tok/s 低于理论值 308 tok/s**

```
1/TPOT × 16 并发 = 19.28 × 16 = 308.5 tok/s
实测 output_throughput        = 251.5 tok/s
差额 18.5% = prefill 抢占 + 调度开销 + 首 token 不产 token
```

### 一个精度提醒

```
WARNING: vllm bench serve no longer sets temperature==0 (greedy) in requests by default.
```

★ **0.30 起默认不再 greedy** → 采样有随机性 → **两次跑的数字不可完全复现**。
要严格可复现的基线，加 `--temperature=0`（旧行为）。

## 六、⚠️ v0.30.0 相对 v0.28 的 4 处实测差异（跑 bench 前必读）

| # | 差异 | 影响 | 应对 |
|---|---|---|---|
| 1 | **默认不再 greedy**（`temperature` 由服务端定） | 结果不可复现 | 加 `--temperature=0` |
| 2 | 终端**只打印 Mean/Median/P99**，不再有 P50/P90/P95 四连 | 旧解读卡模板失效 | 要更多分位用 `--metric-percentiles` |
| 3 | **`rtfx` 恒为 0.0**（仅 ASR 有意义） | 别拿它当性能指标 | 忽略该字段 |
| 4 | `Peak concurrent requests` (26) **>** `--max-concurrency` (16) | 旧解读"远小于它=瓶颈在生成"失效 | 理解为 chunked prefill 的正常现象 |

> 另：0.30 的 `vllm bench serve --help` 只打印分组摘要，要看全量参数得用 `--help=all`；查单个参数用 `--help=<参数名>`。

## 七、给自研栈（Lyngor）的对照口径

- 同负载、同并发、同长度下，`output token throughput` 与 `TTFT p99` 是跨栈对比的核心指标
- vLLM 的服务端指标在 `/metrics`（Prometheus，含 `vllm:num_requests_running` 等），benchmark 之外可留一手
- **对比时必须对齐**：input-len / output-len / num-prompts / concurrency / request-rate / temperature，缺一项数字就不可比
