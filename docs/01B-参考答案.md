## Q1: 一次 POST /v1/chat/completions 从 entrypoint 到 EngineCore 的调用链？

```
HTTP POST /v1/chat/completions
  └─ vllm/entrypoints/openai/api_server.py（路由在 openai/chat_completion/ 子模块）
      └─ AsyncLLM（vllm/v1/engine/async_llm.py，AsyncLLM extends EngineClient）
          ├─ generate()      async_llm.py:624
          └─ add_request()   async_llm.py:347
              └─ EngineCoreClient 通信（v1/engine/core_client.py）
                  ├─ AsyncMPClient（独立进程，core_client.py:1046） ← 服务端默认
                  └─ InprocClient（进程内，core_client.py:333，离线 LLM API 用）
                      └─ EngineCore（v1/engine/core.py:105）
                          └─ run_busy_loop()（core.py:1422，EngineCoreProc 起独立进程跑）
                              └─ step()（core.py:608）
```

**每跳传的对象**：API 层组 `EngineCoreRequest`（prompt/tokens/sampling params/request_id）→ `scheduler.add_request`（core.py:503）内部转 `Request` → `schedule()` 产出 `SchedulerOutput` → worker 返回 `model_output` → `scheduler.update_from_output` 产 `EngineCoreOutputs` → client 侧组 `RequestOutput`。

## Q2: Scheduler 在什么时机把请求加入/移出 batch？

- **入队**：`EngineCore.add_request`（core.py:503 调 `scheduler.add_request`）——请求进来先进 waiting 队列。
- **入批**：每次 `step()` 调 `scheduler.schedule()`（scheduler.py:535），把 waiting 请求按策略编排进 prefill/decode 计划（running 列表 + scheduled 批）。
- **移出**：① 完成时 `finish_requests`（core.py:515，FINISHED_ABORTED）；② `_process_aborts_queue`（core.py:613 附近，执行期间收到的 abort）；③ 被抢占（见 Q3）。
- **数据结构**：输入输出契约在 `v1/core/sched/interface.py`（SchedulerInterface）+ `output.py`（SchedulerOutput）+ `utils.py`。

## Q3: 显存不够时 preemption 怎么触发？swap 还是 recompute？

- **触发**：`schedule()` 在为 running 请求分配新 KV block 不足时，选 victim 抢占（scheduler.py:716 附近选 running 中排序靠后的请求），调 `_preempt_request`（scheduler.py:1452）。
- **策略**：**主路径 = recompute（重计算），v0.28 的 V1 引擎没有 CPU swap**。全 v1 目录里 "swap" 只出现在：① GPU 内 block 区域重排（`attention/backends/utils.py:925` 的 needs_swap，是 tensor 搬运不是 offload）；② 可选的 `v1/simple_kv_offload/disk_backend.py`（显式开启的磁盘卸载特性）。
- 另注意 `recompute_kv_load_failures`（scheduler.py:146/164）：KV 加载失败时的重算策略可配置。
- **和新版教程的差异**：经典教程讲 swap vs recompute 二选一，v0.28 主路径只剩 recompute——这是你这版需要更新的认知点。

## Q4: KV cache 的 block 怎么分配/释放？kv_cache_layout.py 在算什么？

- **分配**：`KVCacheManager.allocate_slots(request)`（kv_cache_manager.py:343）；前缀命中复用 `get_computed_blocks`（:228）；`get_num_common_prefix_blocks`（:632）= 前缀缓存复用判定。
- **释放**：`free(request)`（:566）；block 物理页由 `v1/core/block_pool.py` 管理。
- **kv_cache_layout.py**：算的是**每个 token 的 KV 占多少字节、page/block 大小、按层（含 GDN/mamba 与 attention 对齐）的显存布局**。"GPU KV cache size / Maximum concurrency"（日志里 kv_cache_utils.py:1869 的输出）就来自这套计算。
- 你日志里的 `Setting attention block size to 784 tokens ... >= mamba page size`（interface.py:911/935）就是 mamba page 与 attention page 取整对齐的实际执行点。

## Q5: attention backend 是怎么被选中的？

- `v1/attention/selector.py`：`get_attn_spec_kind`（:62）判定模型 attention 种类（标准/GDN/mamba/MLA…）→ `get_attn_backend`（:102）→ 依据规范 + 平台能力 + 配置从 `backends/registry.py` 注册的后端里选实现。
- 混合注意力模型（qwen3_5）额外走 `get_mamba_attn_backend`（:215），所以 GDN 部分选 `gdn_attn.py`/`linear_attn.py`，标准部分选 `flash_attn.py`——一个模型两种后端并行。
- 可用 `--attention-backend` 等配置强制指定。

## Q6: 生成完成后 token 如何回到 detokenizer 并流式吐出？

```
EngineCore.update_from_output → EngineCoreOutputs（每步输出）
  └─ AsyncLLM._run_output_handler()（async_llm.py:750）从 client 取输出
      └─ OutputProcessor（v1/engine/output_processor.py）
          ├─ RequestState.make_request_output（:283）组装 RequestOutput
          └─ StreamingUpdate（增量更新，:113）
              └─ FastIncrementalDetokenizer（v1/engine/detokenizer.py:168）
                  ├─ update()（:96）：新 token 增量解码
                  ├─ decode_next()（:211)
                  └─ get_next_output_text()（:149）→ 增量文本
                      └─ api_server 以 SSE chunk 吐出（stream=True 时逐片发）
```

**要点**：detokenizer 是**增量**的（不是整句回头解），每步只解新增 token，这样才能流式；`delta` 参数控制输出差异文本。
