## V0 vs V1（记这 6 行）

| 事 | V0 | V1（现在这棵） |
|---|---|---|
| 引擎类 | `LLMEngine` / `AsyncLLMEngine` | `v1/engine/`：AsyncLLM + EngineCore（老名只剩 7 行别名） |
| 进程 | 单进程为主 | APIServer / EngineCore 两进程；离线走 Inproc 单进程 |
| 抢占 | swap（KV 挪 CPU）或 recompute | 只有 recompute |
| 调度 | 每 step 重排，一个 `max_num_seqs` 管两头 | `SchedulerOutput` 契约 + prefill/decode 分开给预算 + 两级上限 |
| 后端 | 全局单后端 | 按 attention 种类选；混合模型两后端并存 |
| detokenize | 整句回解 | 增量，每圈只解新 token |

## 0. 骨架：一次请求跨 2 进程

```
进程 A：APIServer      ① API 层（FastAPI / 路由 / SSE）
                       ② AsyncLLM（InputProcessor 文本→token id；OutputProcessor 回文本）
        ╎ zmq ROUTER→DEALER（请求）  /  PUSH→PULL（结果）
进程 B：EngineCore     ③ 收件排队 → ④ Scheduler → ⑤ Model Runner → ⑥ 回流出口
        ╎ 结果回进程 A（EngineCoreOutputs）
进程 A                 ⑦ OutputProcessor + 增量 Detokenizer → SSE
```

- 单卡 uniproc 无独立 Worker 进程：`gpu_worker` / `model_runner` 都在 EngineCore 进程内。
- 循环体 = ④→⑤→⑥，每圈 1 个 decode token；③ 只在新请求来时走。
- 第 5 层默认 Model Runner V2（`v1/worker/gpu/`）。日志无 `Using V2 Model Runner` → 回退 `v1/worker/gpu_model_runner.py`。

## Q2: Scheduler 何时加入/移出 batch？

**答案**：入队 = `add_request`；入批 = 每圈 `schedule()`（waiting→running，按 token 预算切）；移出三条路 = 完成 / abort / 抢占。输入 waiting+running，输出 `SchedulerOutput`，回头 `update_from_output` 折成 `EngineCoreOutputs`。

- 入队 `core.py:489` → `scheduler.py:2485`，进 waiting。
- 入批 `scheduler.schedule()` `scheduler.py:556`。
- 移出：① `finish_requests` `:2513`；② `_process_aborts_queue` `core.py:788`；③ 抢占（Q3）。
- 契约：`sched/interface.py:38`（`SchedulerInterface`）+ `output.py:232`（`SchedulerOutput`）+ `utils.py`。
- 两级上限（`scheduler.py:124-131`）：`max_num_running_reqs` = runner 槽位；`max_num_active_reqs` = 进 RUNNING 的准入。**进 RUNNING ≠ 占槽位**。准入判定 `:876-877`（`num_running >= max_num_active_reqs` 跳出；`num_running` 含 `num_waiting_for_streaming_input`），槽位断言 `:1359`。CLI：`--max-num-active-seqs`。
- prefill 节流（`scheduler.py:597-602`）：非 cadence 对齐的 step 推迟 prefill，除非已饱和；单调请求时 `long_prefill_token_threshold` 不限长。

## Q3: 显存不够时 preemption 怎么触发？swap 还是 recompute？

**答案**：只有 **recompute**，无 CPU swap。running 请求要不到新 block → 选 victim（FCFS 下队尾）→ `_preempt_request` 释放 block、置 `PREEMPTED`、`num_computed_tokens=0`、回 waiting 队首 → 下圈整段重算。

- 触发 `scheduler.py:759-798`（PRIORITY 下 `max(running, key=(priority, arrival_time))`，否则 `running.pop()` 即队尾）；`_preempt_request` `:1538`。
- 核心：`_free_request_blocks()` `:2628` → `status=PREEMPTED` → `num_computed_tokens=0` → `waiting.prepend_request`。
- v1 里 "swap" 只剩两处，都不 offload：GPU 内 block 重排（`attention/backends/utils.py:934` `needs_swap`）；可选卸载后端（`simple_kv_offload/disk_backend.py`、`kv_offload/`）。
- `recompute_kv_load_failures`（`scheduler.py:155/173`，用于 `:2188/:3203/:3228/:3264`），默认 `True`。
- 抢占时联动 aux_output（`:1554-1555`）：`aux_output_connector.request_finished(request)`。
- `defer_block_free`（`:156-181`）：重叠 batch + KV consumer → 延迟释放 block，防"仍在写的 block 被重分配"。栅栏 `sched_step_seq` / `processed_step_seq`（`:1512/:1935/:2624/:2645`）。

## Q4: KV block 怎么分配/释放？kv_cache_layout.py 算什么？

**答案**：分 = `allocate_slots()`（先 `get_computed_blocks()` 白拿前缀命中）；还 = `free()`；物理页归 `block_pool.py`。`kv_cache_layout.py` 算每 token 每层 KV 字节 + page/block 大小 + 混合注意力页对齐 → 日志 `Setting attention block size to 784 tokens` 就是它算的结果。

- 分配 `kv_cache_manager.py:371 allocate_slots`（11 参数）；前缀 `:264 get_computed_blocks`；复用判定 `:681 get_num_common_prefix_blocks`。
- 释放 `:610 free`；物理页 `v1/core/block_pool.py`。
- layout：`KVCacheLayout` Enum `v1/kv_cache_layout.py:15`（5D stride 置换）。KV 容量日志 `update_kv_cache_capacity()`（`kv_cache_utils.py:2423`，打印 `:2434`）。
- 784 出处 `platforms/interface.py:973`（量化 KV 变体 `:792`）：mamba page 与 attention page 取整对齐。
- 每 step 开头通知协调器：`KVCacheManager.new_step_starts()` `:954` → `KVCacheCoordinator.new_step_starts()`（`kv_cache_coordinator.py:467`）。

## Q5: attention backend 怎么选中？

**答案**：先判 attention 种类（标准/GDN/mamba/MLA…），再叠平台能力 + 配置，从 `backends/registry.py` 注册表挑实现。混合模型一个模型两种后端。`--attention-backend` 可强制。

- `selector.py:64 get_attn_spec_kind` → `:105 get_attn_backend`。
- 混合注意力（qwen3_5）另走 `:228 get_mamba_attn_backend`：GDN 部分 `gdn_attn.py` / `linear_attn.py`，标准部分 `flash_attn.py`。
- 注册入口 `backends/registry.py:273 register_backend`。

## Q6: 生成完 token 如何回 detokenizer 并流式吐出？

**答案**：`update_from_output` 把本圈新 token 折成 `EngineCoreOutputs` 送出 EngineCore → 进程 A `_run_output_handler` 取回 → `OutputProcessor` 用增量 detokenizer 只解新增 token → `RequestOutput` → asyncio 队列 → SSE。

```

  └─ AsyncLLM._run_output_handler()（async_llm.py:791）
      └─ OutputProcessor（output_processor.py:464）
          ├─ RequestState.make_request_output（:299）→ RequestOutput
          └─ StreamingUpdate（:121）
              └─ FastIncrementalDetokenizer（detokenizer.py:166）
                  ├─ update()（:96）
                  ├─ decode_next()（:209）
                  └─ get_next_output_text()（:148）→ 增量文本
                      └─ serving.py:451 chat_completion_stream_generator → SSE
```

- 增量，不是整句回解；`delta` 控差异文本。基类 `BaseIncrementalDetokenizer`（`detokenizer.py:69`）。非流式 `serving.py:917 chat_completion_full_generator`。

## 附 1：一页速记

1. 文本→token id 在 AsyncLLM 的 InputProcessor。EngineCore 收 token id。
2. 入队 `add_request`；入批 `schedule()`；移出 = 完成 / abort / 抢占。
3. 抢占 = recompute（`num_computed_tokens=0` 回 waiting 队首）。无 CPU swap。
4. KV：`allocate_slots` 要、`free` 还、`block_pool` 管页；`kv_cache_layout` 算字节与页对齐。
5. 后端 = attention 种类 → 平台能力 → 配置。混合模型两后端并存。
6. 回流 = `update_from_output` → 跨进程 → 增量 detokenize → SSE。
7. 一次请求 2 个进程。Worker 不是独立进程。

## 附 2：三条不变式

- `EngineCore.step()` 骨架：`schedule` → `execute_model(non_block)` → `update_from_output`（`core.py:633`）。空转时 `has_requests()` 假 → 首行返回，不跑 GPU。
- `execute_model` 返回 `None`，状态挂 `self.execute_model_state`，`sample_tokens` 再取（异步调度）。
- `_prepare_inputs` 首句 `self.input_batch.block_table.commit_block_table(num_reqs)`（调度器 block id → attention 地址）。

## 附 3：最易搞错 4 处

1. 无独立 Worker 进程。
2. `step()` 空转不是 bug。
3. `update_from_output` 单数，由 `step()` 内部调。
4. `abort_requests` 复数；`_handle_client_request` 私有（`core.py:1597`）。
