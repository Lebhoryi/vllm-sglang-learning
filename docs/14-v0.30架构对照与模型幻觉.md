## 1 一句话

**模型答 vLLM 一律不可信。** V0 时代的知识在权重里压过 V1，两条前沿模型都按 V0 架构答，连"v0.30 这个版本号"都不认。

```bash

```

## 2 模型的 5 个典型错误

两条路由**犯完全相同的错**，这比它们之间的差异更值得记。

| # | 模型怎么说 | 实际 |
|---|---|---|
| 1 | 「vLLM 没有 v0.30 这个版本号」／当成 v0.3.0 | 版本真实存在：源码 `v0.30.1rc0-60`，49.147 实装 `0.30.0` |
| 2 | `BlockSpaceManager` / `BlockAllocator` / `PrefixCachingBlockAllocator` / `PhysicalTokenBlock` / `swap_in` `swap_out` / `CacheEngine` | **v0.30 里全被移除**。`vllm/core` 目录**根本不存在**。实际是 `KVCacheManager` + `BlockPool` |
| 3 | `Scheduler._schedule_prefills` / `append_slot` / `_preempt` / `_append_slots` | 实际 `Scheduler.schedule()` → `KVCacheManager.allocate_slots()`；回收走 `KVCacheManager.free()` |
| 4 | 「只有完全填满的块才会被缓存和共享」 | 不全。`BlockPool.cache_partial_block()` 注册**块内细粒度前缀边界**，让已存在的块从更细边界命中；哈希粒度是独立的 `hash_block_size`，≠ `block_size` |
| 5 | 没人提 block table 是 **append-only** | `block_pool.py` NOTE #1 明说为保 append-only 才不做块去重 |

**共同点**：它们不是在胡说八道，是在**用 V0 的地图讲 V1 的路**。听起来自洽，一 grep 全崩。

## 4 v0.30 真实对应关系（已抽查，可当参照）

### 块表（block table）

| 概念 | 位置 |
|---|---|
| 管理侧块表（每请求） | `req_to_blocks: defaultdict[str, list[KVCacheBlock]]`，`v1/core/single_type_kv_cache_manager.py:130` |
| 调度侧对外接口 | `KVCacheBlocks.blocks: tuple[Sequence[KVCacheBlock], ...]`，`kv_cache_manager.py:35,41`（外层 = kv_cache_group） |
| worker 侧块表（喂 kernel） | `BlockTable.block_table` = `[max_num_reqs, max_num_blocks_per_req]` int32 tensor，`v1/worker/block_table.py:114-117`；多 group 用 `MultiGroupBlockTable` `:289-290` |
| 语义（最硬证据） | `slot_ids = block_numbers * block_size + block_offsets`，`block_table.py:469-479` → 存的是**物理块号** |

### 分配与回收

| 动作 | 链路 |
|---|---|
| 分配 | `KVCacheManager.allocate_slots()` `:371` → `KVCacheCoordinator.allocate_new_blocks()` `kv_cache_coordinator.py:277` → `SingleTypeKVCacheManager.allocate_new_blocks()` `:366` → `BlockPool.get_new_blocks()` `block_pool.py:660` → `free_block_queue.popleft_n()` |
| 回收 | `KVCacheManager.free()` `:610`（逆序释放，尾块先出）；full attention 在请求结束前不释放 |
| 逐出 | `KVCacheManager.evict_blocks()` `:655`、`reset_prefix_cache()` `:664` |
| 空闲块管理 | `FreeKVCacheBlockQueue` —— **双向链表**（不是 deque），`kv_cache_utils.py:246-297`，队首 LRU |

### 前缀缓存

| 动作 | 位置 |
|---|---|
| 前缀命中 | `get_computed_blocks()` `:264` → `find_longest_cache_hit()` `single_type_kv_cache_manager.py:791-802` → `BlockPool.get_cached_block()` `block_pool.py:196` |
| 引用计数 | `KVCacheBlock.ref_cnt`，`kv_cache_utils.py:182`；共享靠 `BlockPool.touch()` `block_pool.py:746-762` |
| hash → block 索引 | `BlockHashToBlockMap`，`block_pool.py:33`（字段 `:179`） |
| 细粒度前缀边界 | `BlockPool.cache_partial_block()` `block_pool.py:447` |
| `ref_cnt == 0` 时 | 只入 free queue 当淘汰候选，**不释放内容、不删哈希**（`block_pool.py:41-44`、`:785-797`）；等块被真正重新分配时才由 `_maybe_evict_cached_block` 清哈希 |

## 5 block table 的 4 条硬事实（M4 用）

1. **append-only** —— `block_pool.py:46-50` NOTE #1：为不让已分配块号变化，故意不做块去重
2. **prefill 和 decode 共用同一张表** —— decode 不重建、不重排，只是长度增长
3. **`ref_cnt` 归零 ≠ 立即释放** —— 降级成"缓存块"，直到被逐出
4. **被共享的物理块仍是完整块**，但哈希粒度是独立的 `hash_block_size`，比 `block_size` 细

> 第 4 条是"只有填满的块才共享"这句话的正解：物理块确实要满，但**查找项**可以落在块内更细的边界。

## 6 附：路由对照结论（实验副产物，留 4 行）

同一题发给两条路由，质量无差异、速度差 2–4 倍：

| 指标 | opencode-go（跨洋） | lyngpt（内网） |
|---|---|---|
| 任务 A 总耗时 | 85.1 s | **20.6 s** |
| 输出 token | 13,082 | **4,549** |
| 首字延迟 | 1,882 ms | **1,204 ms** |

- 慢的两层原因：**196 ms 跨洋 RTT**（吃首字）+ **网关排队**（吃稳态 tok/s）
- 因果实验：`delayproxy.py` 注入 2 s 延迟 → 吞吐纹丝不动、TTFT 涨 4.3 s ⇒ **RTT 不是 tok/s 瓶颈**
- 陷阱：调高 `reasoning` 档位会让 tok/s 读数变高（思考 token 解码更快），但**更慢更贵**
