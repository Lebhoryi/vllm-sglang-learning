## 一、先看什么

打开后默认停在场景①。**不要急着点播放**，先花 30 秒认清六个区域：

```
┌ 顶栏：场景 / 播放控制 / 速度 / step·事件·抢占·KV 四个计数器 ─────────┐
├──────────────┬───────────────────────────────┬──────────────────────┤
│ 场景说明      │  scheduler.py 623-866 全文     │ 三个预算条            │
│ 参数与开关    │  ← 当前执行的行走到这里          │ KV block 池（方格）   │
│ RUNNING 队列  │    已走过的行会变亮             │ WAITING / 被抢占      │
├──────────────┴───────────────────────────────┴──────────────────────┤
│ 旁白（L行号 + 这句话在干什么） / 时间轴（黄竖线=关键事件） / 日志流     │
└─────────────────────────────────────────────────────────────────────┘
```

- **旁白永远是第一信息源**。它说的是"这一步在判断什么、为什么"，
  左上角的 `L数字` 就是当前正在执行的**真实源码行号**。
- **代码面板会跟着旁白滚动**，已走过的行变亮（暖黄），当前行蓝底高亮。
  所以你可以只用眼睛跟着代码跑一遍。
- **KV 池的方格**按请求染色。哪一块归谁、什么时候被释放，一眼可见 ——
  抢占的本质就是"把别人的方格抢过来"。

### 播放控制

| 按钮 | 作用 | 什么时候用 |
|---|---|---|
| `▶ 播放` / `Space` | 按速度连续推进 | 先整体过一遍节奏 |
| `⏭ 事件` / `→` | 前进**一个微事件**（代码的一小步） | 逐字精读时用 |
| `⏭⏭ 一步` / `Shift+→` | 跑完一整个 `schedule()` 调用 | 想看"一步"的完整结果 |
| `⚡ 关键` | 跳到下一个关键事件（抢占/提交/skip/break） | **最常用**，跳过琐碎细节 |

嫌慢就把速度拉到 20-40 事件/秒；场景③④要跑 30 多步才到抢占，直接用 `⚡ 关键` 连点。

## 二、八个场景，各自要盯住什么

每个场景左侧都有说明。下表是"**应该看到什么现象**"，看到了才算读懂。

### ① chunked prefill：预算就是 chunk 上限

- 1 个 300 token 的长 prompt，`max_num_batched_tokens = 128`
- **盯**：`token_budget` 条从 128 → 0 → 重置 → 0，一共吃掉三轮
- **盯**：RUNNING 卡片上的 `c(computed)/t(known)`，从 `c0/t300` 一步步追到 `c300/t300`
- **盯**：旁白里 `long_prefill_token_threshold=0` —— 队列里只有 1 个请求时阈值被置 0（源码 611-615），
  因为"没有别人可以被饿死"
- 关键行：669（算 num_new_tokens）、676（被 token_budget 截断）、815（提交记账）

### ② 防饿死：long_prefill_token_threshold

- 队列里有 2 个请求 → `num_eligible_reqs > 1` → 阈值生效
- **盯**：长 prefill 每次只拿 64 token，另一条 decode 请求始终有配额
- **动手**：把左侧 `long_prefill_threshold` 拉到 0 → 应用并重跑 → 长 prefill 开始独吞预算，
  decode 请求被挤到后面。这就是这个配置项存在的全部理由
- 关键行：611（算阈值）、674（截断）

### ③ 抢占（FCFS）：牺牲的是"最新来的"

- KV 池故意给小（12 块 × 8 token），随 decode 增长慢慢填满
- **盯**：`KV` 计数器爬到 12/12 的那一刻
- **盯**：旁白 `KV 不足 → FCFS 策略选牺牲者：running[-1] = C（队尾 = 最新来的）`
  —— 注意此时正在处理的请求是 **A**，被牺牲的却是 **C**。这是 765/798 行 `pop()` 队尾的效果
- **盯**：C 的卡片变成虚线红框、`computed` 归零、回到 WAITING 区，`被抢占 1` 标签出现
- **盯**：抢占那一步的 `token_budget` 剩余量 —— 因为 868 行，**这一步的 WAITING 段被整段跳过**
- 关键行：748（分配失败）、765（选 victim）、798（pop）、800（`_preempt_request`）

### ④ 抢占（PRIORITY）：全量回滚 778-796

这是整段代码最绕的地方，也是动画最能帮上忙的地方。

- `low(priority=9)` 第 1 步进 running；`hi(priority=0)` 第 2 步才到 → running 顺序是 `[low, hi]`
- 第 3 步处理 `hi` 时 KV 不足，victim = `max(priority)` = **前面的 low**
- **盯**：旁白出现 `victim_index(0) < req_index → req_index -= 1`（775 行）
- **盯**：紧接着 `low 本步已被调度过 → 回滚它的记账（预算还给池子）`（778-796）
  —— `token_budget` 和 `input_budget` 的条会**回弹**
- 为什么必须回滚：`low` 在 `req_index` 走过它时已经扣过预算、记过 `num_scheduled_tokens`，
  现在它被踢走了，这些账必须原样还回来，否则 1354-1358 的断言就会炸
- 对照场景③：**同一段抢占循环，两种受害者** —— FCFS 抢队尾，PRIORITY 抢最弱优先级

### ⑤ 投机解码：draft token 怎么进批（825-840）

- 每个请求带 2 个 draft token，`token_budget` 128
- **盯**：`num_new_tokens = num_tokens_with_spec(27) + placeholders(0) - computed(24) = 3`
  —— 一次带 1 个真实 token + 2 个 draft
- **盯**：`num_scheduled_spec_tokens = 3 + 24 - 25 - 0 = 2`，然后 `spec_token_ids = []`（840 行）
- **盯**：紫色 `draft 2` 标签在卡片上出现又消失

### ⑥ 异步调度：placeholder 与"避免多发一步"（630-644）

- `P1` 以**中途状态**开场：`outputs=3` + 1 个在途 placeholder，`max_tokens=4`
- **盯**：第一步 P1 就被 skip（旁白 630 行），理由是"即使这个 placeholder 对应的 draft 全被拒，
  也已经到上限了"
- **盯**：跳过 P1 的这一步末尾，它的 placeholder 转正 → P1 恰好结束
  —— 这就是 630-644 换来的收益：不发那一步多余的请求，decode 批次的形状保持统一
- `P2` 是常规 async 请求，对照看它"采样 → 占位 → 下一步转正"的节奏

### ⑦ DP prefill 均衡：defer_prefills（601-603 / 652-656）

- 第 1 步 P（长 prefill）和 D（短 prompt）同时进 running
- 第 2 步起 `defer_prefills = true` → **盯**：P 被 652 行的 continue 跳过，只有 D 在推进
- 读 `defer_prefills` 的公式（601-603）：`throttle && !capacity_bound && 存在非 chunk 请求`
  —— 意思是"这一步本来就不是给 prefill 用的，那就把它让给 decode"
- DP 部署下用来抹平各 rank 的步进节奏

### ⑧ 重算 vs prefix cache：被抢占到底多贵

- 三条 64-token prompt，抢占后对比"computed 归零"和"prefix cache 保住前 32 个"
- **动手**：把左侧 `prefix cache 命中` 开关关掉 → 应用并重跑
- **盯**：同一个请求的 `被抢占 N` 次数与总步数的变化
- 这条直接回答 docs/02 附录里的问题：**为什么 prefix caching 对调度器这么重要** ——
  它不是省显存，是省**重复计算**。KV 越紧张抢占越频繁，这一项的价值就越大

## 三、参数面板能玩的实验

展开左侧「参数与开关」，改完点「应用并重跑」。推荐这几个：

| 改动 | 预期现象 | 说明什么 |
|---|---|---|
| `max_num_batched_tokens` 128 → 32 | 每个请求被切得更碎，步数暴涨 | 预算就是 chunk 粒度 |
| `num_gpu_blocks` 调小 | 抢占提前出现、次数变多 | KV 压力是抢占的唯一原因 |
| `policy` fcfs → priority | 受害者从"队尾"变成"最弱优先级" | 760-766 的分支 |
| `long_prefill_threshold` → 0 | 长 prefill 独吞预算 | 611-621 |
| `draft tokens / req` 2 → 4 | 每步带更多 token，`num_scheduled_spec_tokens` 变大 | 825-840 |
| `defer_prefills` 打开 | prefill chunk 被跳过 | 652-656 |
| `异步调度` 打开 | 卡片出现 `ph` 标签，采样延迟一步转正 | 630-644 的前提 |
| `max_num_seqs` 调到 2 | WAITING 不再接纳新请求（877 行 break） | 877 的闸门 |

## 四、和 docs/02 的关系（一处需要修正）

docs/02「专题 1」第 2 问写的是：

> preemption 在什么条件下触发？**swap 与 recompute 怎么选？**

**这一问基于 V0 的旧概念，在 V1 里已经不成立**：

- V1 的 `scheduler.py` / `request.py` 里**没有 swap**（`grep -rn "swap" vllm/v1/core/sched/` 为空），
  V0 的 `vllm/core/scheduler.py`（含 `_swap_out` / `SWAPPED` 状态）在 V1 重构中已整体删除。
- V1 抢占**只有一种方式：recompute** —— `_preempt_request()`（1538-1581）把
  `num_computed_tokens` 直接归零、释放全部 KV block、把请求 prepend 回 waiting 队列。
- 于是"抢谁的 KV"完全由 block 池的供需决定，不再有"换到 CPU 内存"这条路。
  这也是场景③④能在一屏里讲清楚的原因。

动画里能直接验证这一点：**盯被抢占请求的卡片** —— `computed` 瞬间归零、块全部消失、
回到 WAITING 重新排队，没有任何"换出"中间态。
