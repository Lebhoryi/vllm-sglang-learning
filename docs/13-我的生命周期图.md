## 画的时候答这 3 问

1. 请求在哪一站**从「文本」变成「token id」**？
   → **② AsyncLLM** 里的 `InputProcessor.process_inputs`（先 `renderers/` 渲 chat 模板，再 tokenize）。
   不在 EngineCore、也不在 Model Runner —— 引擎侧收到的已经是 `EngineCoreRequest`（token id 数组）。

2. 输出 token 从哪一站开始**回流**给客户端？
   → **⑤ Sampler 出 token_id 那刻起**算生成完毕；打包跨进程发生在 **⑥ 末尾**（`output_queue` → `zmq.PUSH`）；
   真正变回文本在 **⑦**（`process_outputs` 里做增量 detokenize）→ SSE。
   跨进程的分界点是 ⑥，读者关心的"回流起点"是 ⑤。

3. 第 ③ 站 `step()` 循环，输出 39 token 的那次请求，转了几圈？
   → **约 39 圈**：首圈 prefill 一次吃完整条 prompt，之后每圈 1 个 decode token。
   偏差来源：chunked prefill 把长 prompt 切片、开 speculative decoding（一圈出多个 token）、async scheduling（一圈拆两拍）。

## 直读源码时最容易搞错的 4 处

1. **没有独立 Worker 进程** —— Worker / Model Runner 长在 EngineCore 进程里。
2. **`step()` 空转不是 bug** —— `has_requests()` 为假时第一行就返回，不跑 GPU，只 `sleep(0.001)` 等活。
3. **`update_from_output` 不是 `update_from_outputs`** —— 现在叫单数，且由 `step()` 内部调用，不是 EngineCore 外面调。
4. **`abort_request` 已改复数 `abort_requests`**；`handle_client_request` 变私有 `_handle_client_request`。
   （另：`Launcher` 类、`TokenizerGroup`、`Processor` 三个名字都已消失或改名，搜不到别怀疑自己。）

## ⚠️ 重要负面发现：一次请求几乎不留日志

108 行日志里，那次 curl **只产生 1 行**：

```
(APIServer) INFO: 127.0.0.1:36854 - "POST /v1/chat/completions HTTP/1.1" 200 OK
```

**没有** `Added request`，没有 per-step 调度记录。

### 三条结论

1. **上一轮给的 `Added request` 提示是错的** —— 这行在 serve 日志里不存在
2. **日志只能证明「进程边界」，证明不了「进程内链路」** —— ③④⑤⑥ 内部怎么走必须读源码
3. **`Engine 000:` 统计行是异步低频的** —— 请求 08:46 发生，统计行 **09:28** 才打印（42 分钟后），不能当实时流程看

> 所以：粗粒度图靠**源码**画，日志只做交叉验证。
